# Content Moderation

## TL;DR
Content moderation in LLM systems ensures that the inputs sent to the model and the outputs generated by the model are safe, non-toxic, and topically relevant. Because foundation models can generate essentially anything, production systems require independent classification layers—using dedicated APIs or custom models—to block hate speech, self-harm instructions, or off-topic queries before they cause brand damage or liability.

---

## The Need for Independent Moderation

While modern LLMs undergo safety training (RLHF) to refuse harmful prompts, this alignment is not perfect and can be bypassed via jailbreaking. 

Therefore, a robust production architecture relies on an independent moderation layer. This layer evaluates the content without generating text, acting as a binary (Safe/Unsafe) gatekeeper.

Moderation is applied at two boundaries:
1. **Input Moderation:** Scanning the user's prompt to prevent the system from wasting compute on malicious queries and to thwart jailbreaks.
2. **Output Moderation:** Scanning the LLM's generated response to ensure no toxic content, PII leaks, or hallucinations slip through.

## Managed Moderation APIs

The fastest way to implement moderation is using purpose-built APIs. These endpoints are heavily optimized for latency and are continually updated with new attack vectors.

### 1. OpenAI Moderation API
A free (for OpenAI developers) endpoint that classifies text into categories like `hate`, `self-harm`, `sexual`, and `violence`.
- **Use Case:** Broad-strokes safety for user-facing chatbots.
- **Limitation:** It is a black box. You cannot adjust its sensitivity or add custom categories.

### 2. Azure AI Content Safety
An enterprise-grade service that detects harmful user-generated and AI-generated content.
- **Advantage:** Allows developers to set sensitivity thresholds (e.g., block all mild sexual content, but allow mild violence in a gaming context). It also detects prompt injection and jailbreak attempts natively.

## Custom Classifiers and Topic Filtering

General moderation APIs only check for universally harmful content. However, enterprise applications often need **domain-specific moderation** (topic filtering). 

If you build a customer support bot for an airline, you don't just want to block hate speech; you want to block queries about the user's political opinions or competitors' pricing.

### Implementing Topic Filters
1. **Fast ML Classifiers:** Training a lightweight model (like a Support Vector Machine or a small BERT model) to classify intent as `in_domain` or `out_of_domain`. This is extremely fast and cheap.
2. **LLM-Based Routers:** Using a smaller, cheaper LLM to classify the input. 
   *Prompt:* "Is this query strictly related to airline travel? Output YES or NO."
3. **Vector Similarity:** Embedding the user's query and comparing it against a known database of "allowed" topics. If the cosine distance is too far from any allowed topic, block it.

## Actions: Block vs. Warn vs. Log

When a moderation flag is triggered, the system must decide how to handle it.

- **Block (Hard Stop):** Used for egregious violations (hate speech, clear PII leaks). The API call is aborted, and a generic error message is returned to the user.
- **Warn/Deflect:** Used for off-topic queries. The system intercepts the prompt and replaces the LLM's generation with a scripted deflection: "I'm a banking assistant, I can only help with account inquiries."
- **Log (Shadow Mode):** Used when testing new moderation rules or for edge-case content. The system allows the query to proceed but flags it in the observability platform (like LangSmith) for human review later. This prevents false positives from ruining the user experience while still gathering data.

## Production Implications

Moderation adds latency. If you use an external Moderation API, you must wait for the network round-trip before executing the main LLM call. 

To mitigate this, production systems often run input moderation **asynchronously**. The system immediately sends the prompt to the main LLM to begin generation, while simultaneously sending it to the moderation API. If the moderation API flags the input, the main LLM process is killed mid-stream, and the connection to the client is severed. 

## Common Mistakes

- **Blocking everything on "mild" flags:** Setting custom classifiers too strictly, resulting in severe false positives (e.g., blocking a query about a "broken arm" on a medical site because it triggered a "violence" filter).
- **Relying on the main LLM to moderate itself:** Asking the main model "Was your response toxic?" is a conflict of interest. An independent system must perform the check.
- **Synchronous output moderation on long streams:** Waiting for a 1000-token response to finish so you can send the whole thing to a moderation API defeats the purpose of streaming. Output must be moderated in chunks.

## Interview Questions

**Q: Why should you use an external Moderation API instead of just relying on the safety training of GPT-4?**
**A:** Model alignment is probabilistic and can be bypassed via jailbreaking or complex edge cases. An independent Moderation API acts as a deterministic, defense-in-depth layer. Furthermore, moderation APIs are typically specialized classifiers that run faster and cheaper than evaluating safety within the main generation loop.

**Q: How would you prevent a customer service chatbot from answering questions about a competitor?**
**A:** I would implement a topic filter using a fast intent classifier or a semantic router. Before the prompt reaches the LLM, the classifier evaluates if the intent is related to our products. If it detects a competitor's name or an out-of-domain topic, it intercepts the request and returns a scripted deflection message.
