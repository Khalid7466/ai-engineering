# Tool Design Patterns

## TL;DR
Designing effective tools for an AI agent is different from designing an API for a human developer. Tools must be designed around the LLM's strengths and weaknesses, favoring idempotency, clear error messages over stack traces, and safe (read-only) operations whenever possible.

---

## Granular vs Composite Tools
- **Granular:** `get_user_id(name)`, `get_user_billing(id)`, `cancel_subscription(id)`
- **Composite:** `cancel_user_subscription(name)` (which handles the ID lookup, billing check, and cancellation internally).

**When to use which:** 
If the process requires reasoning at each step (e.g., "Only cancel if the billing is overdue"), use granular tools so the LLM can make the decision. If the process is a deterministic sequence, use a composite tool. Hiding deterministic logic inside a composite tool saves tokens and reduces the chance of the LLM making a routing error.

## Safe vs Unsafe Tools
- **Safe (Read-only):** `search_web`, `read_file`, `get_stock_price`. These can be executed freely by the agent.
- **Unsafe (State-changing):** `drop_table`, `send_email`, `execute_bash`. 

Unsafe tools should almost always require a Human-in-the-Loop (HITL) approval step before the application layer executes the JSON payload generated by the LLM. 

## Idempotency
Because agents often get stuck in ReAct loops and might retry the same tool call multiple times, state-changing tools *must* be idempotent. 
If the agent calls `charge_credit_card(amount=50, id=123)` twice by accident, the second call should return a safe message like "Charge already processed," rather than billing the user twice.

## Error Message Design
When a tool fails in standard software, it might throw a `NullPointerException`. If you return a raw stack trace to an LLM, it often gets confused.
**Agentic Error Handling:** You must catch exceptions in your tool execution layer and translate them into actionable natural language for the model.
- **Bad return:** `Error 500: KeyError 'uuid'`
- **Good return:** `Error: You did not provide a valid 'uuid'. Please use the 'search_user' tool first to find the correct UUID, then try again.`
The model reads this error *as an observation* and will use it to formulate its next thought.

## Tool Result Formatting
LLMs have finite context windows. If a SQL execution tool returns 50,000 rows of raw JSON, the context window will blow up.
Tools should heavily format and truncate their own output before returning it to the agent. Return aggregations, summaries, or the first 50 rows with a note: `[Output truncated to 50 rows. Total rows: 50,000. Consider refining your SQL query.]`

## Production Implications
The most common point of failure in production agents is a mismatch between the LLM's generated arguments and the actual function signature. Use a validation library (like Pydantic). If validation fails, do not crash the app. Catch the `ValidationError`, convert it to a string, and pass it back to the agent as a tool result. The agent will usually apologize and fix the JSON syntax on the next turn.

## Common Mistakes
- **Returning raw stack traces:** Sending internal system errors to the model, causing it to hallucinate weird workarounds.
- **Missing idempotency:** Allowing a confused agent to send the same email 5 times because the tool didn't check state.
- **Overly generic composite tools:** Building a "do_everything" tool with 20 optional parameters, which the model inevitably misuses.

## Interview Questions
- **Q: Why is idempotency critical when designing tools for an LLM agent?**
  - A: Because LLMs are probabilistic and may mistakenly call the same tool multiple times or get stuck in a retry loop. Idempotent tools prevent unintended side effects (like double-charging a customer).
- **Q: How should you handle a situation where a tool returns 10MB of text?**
  - A: The tool should truncate the output, return the first chunk, and append a message informing the LLM that the output was truncated, possibly offering another tool to paginate or filter the data.
